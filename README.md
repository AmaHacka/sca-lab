## 1. Краткая теория

Здесь только минимум, нужный для выполнения работы. В конце каждого блока есть ссылки для самостоятельного изучения.

### 1.1. Уязвимости и их идентификаторы

**Уязвимость** — недостаток ПО, который может быть использован для нарушения конфиденциальности, целостности
или доступности. Известные уязвимости публикуются в базах данных под идентификаторами:


| Идентификатор                                  | Кто выдаёт                               | Пример                                 |
| ---------------------------------------------- | ---------------------------------------- | -------------------------------------- |
| **CVE** (Common Vulnerabilities and Exposures) | MITRE и уполномоченные организации (CNA) | CVE-2021-44228 (Log4Shell)             |
| **GHSA** (GitHub Security Advisory)            | GitHub, для пакетов открытых экосистем   | GHSA-jfh8-c2jp-5v3q — тот же Log4Shell |
| **GO-YYYY-NNNN**                               | команда Go (база govulndb)               | GO-2023-2102                           |
| **BDU:YYYY-NNNNN**                             | ФСТЭК России, Банк данных угроз (БДУ)    |                                        |


Одна уязвимость часто имеет несколько идентификаторов (алиасов). grype показывает основной идентификатор
источника и перечисляет алиасы в `relatedVulnerabilities`.

**CWE** (Common Weakness Enumeration) — классификатор *типов* слабостей: CWE-502 «десериализация недоверенных
данных», CWE-22 «обход пути», CWE-79 «XSS». CVE описывает конкретный дефект, а CWE — его класс.

Подробнее: [cve.org](https://www.cve.org), [NVD](https://nvd.nist.gov), [cwe.mitre.org](https://cwe.mitre.org),
[GitHub Advisory Database](https://github.com/advisories), [OSV](https://osv.dev), [БДУ ФСТЭК](https://bdu.fstec.ru).

### 1.2. Оценка уязвимостей: CVSS, EPSS, KEV

**CVSS** (Common Vulnerability Scoring System) — оценка *тяжести* уязвимости от 0 до 10. Базовая оценка
записывается вектором, например `CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:C/C:H/I:H/A:H` (Log4Shell, 10.0):


| Метрика                   | Значения                                           | Смысл                                                   |
| ------------------------- | -------------------------------------------------- | ------------------------------------------------------- |
| AV — вектор атаки         | **N**etwork, **A**djacent, **L**ocal, **P**hysical | откуда может атаковать нарушитель                       |
| AC — сложность            | **L**ow, **H**igh                                  | нужны ли особые условия                                 |
| PR — привилегии           | **N**one, **L**ow, **H**igh                        | какие права нужны нарушителю                            |
| UI — участие пользователя | **N**one, **R**equired                             | нужно ли действие жертвы                                |
| S — область               | **U**nchanged, **C**hanged                         | выходит ли воздействие за пределы уязвимого компонента  |
| C / I / A                 | **H**igh, **L**ow, **N**one                        | влияние на конфиденциальность, целостность, доступность |


Уровень по оценке: 0.1–3.9 Low, 4.0–6.9 Medium, 7.0–8.9 High, 9.0–10 Critical. Этот уровень grype показывает
в колонке `SEVERITY`. В новых записях встречается CVSS v4.0: метрик в нём больше, но принцип тот же.

CVSS говорит, *насколько плохо будет, если уязвимость проэксплуатируют*, но не говорит, *насколько это вероятно*.
Для этого есть:

- **EPSS** (Exploit Prediction Scoring System, FIRST) — вероятность эксплуатации уязвимости в ближайшие 30 дней
(0–100 %) и перцентиль среди всех CVE. Модель пересчитывается ежедневно;
- **KEV** (Known Exploited Vulnerabilities, CISA) — каталог уязвимостей, эксплуатация которых **подтверждена**.
Если уязвимость есть в KEV, её устраняют в первую очередь.

grype объединяет тяжесть, EPSS и KEV в колонке **RISK** (0–100) и по умолчанию сортирует по ней. Отметка
`(kev)` рядом со значением означает, что уязвимость есть в каталоге KEV.

Подробнее: [спецификация CVSS v3.1](https://www.first.org/cvss/v3.1/specification-document) и
[калькулятор](https://www.first.org/cvss/calculator/3.1), [EPSS](https://www.first.org/epss/),
[CISA KEV](https://www.cisa.gov/known-exploited-vulnerabilities-catalog).

### 1.3. Откуда берутся данные об уязвимостях

Уязвимость пакета ОС и уязвимость библиотеки приложения описываются в разных источниках:

- **Дистрибутивы** (Debian Security Tracker, Alpine secdb, Ubuntu, RHEL и т. д.) ведут собственные записи
для своих пакетов. Они учитывают **бэкпорты**: в Debian исправление часто вносится в старую версию пакета
(`2.28-10+deb10u3`), а версия upstream остаётся прежней. Поэтому пакеты ОС сравниваются только с данными
своего дистрибутива.
- **Экосистемы языков** (GHSA для PyPI, npm, Maven, Go, …; govulndb для Go) описывают уязвимые диапазоны версий
пакетов.
- **NVD** описывает уязвимости через **CPE** — идентификаторы продукта вида
`cpe:2.3:a:apache:log4j:2.14.1:*:*:*:*:*:*:*`. Сопоставление по CPE неточное: оно даёт и ложные срабатывания,
и пропуски.

У каждой записи есть **состояние исправления**: `fixed` (есть версия с исправлением, grype показывает её
в колонке `FIXED IN`), `not-fixed` (исправления пока нет), `wont-fix` (мейнтейнеры решили не исправлять,
в таблице — `(won't fix)`), `unknown`.

Если срок поддержки дистрибутива истёк (**EOL**), исправлений для него больше не выпускают. grype
предупреждает об этом.

Подробнее: [Debian Security Tracker](https://security-tracker.debian.org/tracker/),
[Alpine secdb](https://secdb.alpinelinux.org), [спецификация CPE](https://nvd.nist.gov/products/cpe),
[endoflife.date](https://endoflife.date).

### 1.4. SCA и SBOM

**Анализ состава ПО (SCA, композиционный анализ)** — выявление заимствованных компонентов (библиотек,
пакетов ОС, фреймворков) и контроль их известных уязвимостей и лицензий. Современное ПО на 70–90 % состоит
из чужого кода, поэтому большинство уязвимостей приложение наследует от зависимостей. В России этот процесс
закреплён в **ГОСТ Р 56939-2024** «Защита информации. Разработка безопасного программного обеспечения.
Общие требования» (раздел 5.16 «Использование инструментов композиционного анализа»). Стандарт требует вести
перечень заимствованных компонентов, поддерживать его в актуальном состоянии и контролировать в нём известные
уязвимости.

**SBOM** (Software Bill of Materials) — машиночитаемый перечень компонентов ПО: имя, версия, поставщик,
идентификаторы, лицензии, связи между компонентами. Основные форматы:


| Формат        | Кто развивает                                | Особенности                                    |
| ------------- | -------------------------------------------- | ---------------------------------------------- |
| **SPDX**      | Linux Foundation, стандарт ISO/IEC 5962:2021 | исторически ориентирован на лицензии           |
| **CycloneDX** | OWASP, стандарт ECMA-424                     | ориентирован на безопасность, поддерживает VEX |
| **syft-json** | Anchore                                      | «родной» формат syft, самый подробный          |


Компонент в SBOM однозначно идентифицирует **purl** (package URL), например `pkg:pypi/pyyaml@5.3`,
`pkg:maven/org.apache.logging.log4j/log4j-core@2.14.1`, `pkg:golang/golang.org/x/net@v0.7.0`. В purl есть
экосистема, имя и версия, поэтому по нему сопоставление точное.

Главная польза SBOM в том, что его строят один раз при сборке и хранят рядом с артефактом. Когда выходит
новая CVE, достаточно проверить сохранённые SBOM: пересобирать или скачивать образы не нужно.

Подробнее: [ГОСТ Р 56939-2024](https://base.garant.ru/410749342/),
[NTIA: минимальные элементы SBOM](https://www.ntia.gov/report/2021/minimum-elements-software-bill-materials-sbom),
[CycloneDX](https://cyclonedx.org), [SPDX](https://spdx.dev),
[спецификация purl](https://github.com/package-url/purl-spec).

### 1.5. Как работает syft

syft анализирует **источник**: образ из Docker (`syft образ:тег`), каталог (`dir:путь`), отдельный файл
(`file:путь`), архив образа или образ из реестра (`registry:`). Затем запускает **каталогизаторы**. Каждый
из них знает, где конкретная экосистема хранит метаданные установленных пакетов:


| Экосистема     | Откуда syft берёт сведения                                                                                    |
| -------------- | ------------------------------------------------------------------------------------------------------------- |
| Debian/Ubuntu  | `/var/lib/dpkg/status`                                                                                        |
| Alpine         | `/lib/apk/db/installed`                                                                                       |
| Python         | каталоги `*.dist-info` / `*.egg-info` в site-packages; в исходниках — `requirements.txt`, `poetry.lock` и др. |
| Go             | раздел `.go.buildinfo` внутри скомпилированного бинаря: версия Go и все модули                                |
| Java           | `META-INF/MANIFEST.MF` и `pom.properties` внутри JAR, в том числе во вложенных архивах                        |
| Node.js        | `package.json` в `node_modules`, `package-lock.json`                                                          |
| Бинарные файлы | сигнатуры известных программ (python, openssl, busybox, …)                                                    |


Отсюда главное ограничение: **syft видит только то, о чём остались метаданные**. Файл, скопированный вручную
(vendoring), статически встроенная C-библиотека или программа, собранная из исходников без пакетного
менеджера, в SBOM не попадут.

Образ состоит из **слоёв**, по одному на инструкцию Dockerfile. По умолчанию (`--scope squashed`) syft
анализирует итоговую файловую систему. С `--scope all-layers` он заглядывает в каждый слой, в том числе
в файлы, удалённые более поздними инструкциями.

Подробнее: [документация syft](https://oss.anchore.com/docs/), [репозиторий](https://github.com/anchore/syft).

### 1.6. Как работает grype

grype строит SBOM (с помощью встроенного syft) или принимает готовый (`grype sbom:файл.json`) и сопоставляет
каждый пакет с **локальной базой уязвимостей**. БД собирается инструментом vunnel из десятков источников
(NVD, GHSA, govulndb, трекеры дистрибутивов, EPSS, KEV), обновляется ежедневно и скачивается автоматически
(`grype db status`, `grype db update`).

Сопоставление идёт так:

1. пакеты ОС — по данным своего дистрибутива (с учётом бэкпортов);
2. пакеты языковых экосистем — по имени и версии в данных экосистемы (GHSA, govulndb);
3. если ничего не нашлось, иногда по CPE (например, для бинарных файлов).

Результаты можно фильтровать: `--only-fixed` оставляет только уязвимости с доступным исправлением,
правила `ignore` в файле `.grype.yaml` исключают отдельные находки (с обязательным обоснованием `reason`),
документы **VEX** (Vulnerability Exploitability eXchange) сообщают, что продукт не подвержен уязвимости.
Флаг `--fail-on high` возвращает код 2, если есть находки уровня High и выше. На этом строится
**security gate** в CI.

Подробнее: [репозиторий grype](https://github.com/anchore/grype), [vunnel](https://github.com/anchore/vunnel),
[OpenVEX](https://openvex.dev).

### 1.7. Приоритизация и устранение

Находок обычно сотни, и исправить всё сразу невозможно. Порядок обработки определяют факторы:

1. **эксплуатируется ли** уязвимость (KEV, высокий EPSS);
2. **применима ли** она к сервису: используется ли уязвимый код, доступен ли он нарушителю (сетевой сервис
  или утилита, которую никто не вызывает), выполнены ли условия эксплуатации;
3. **тяжесть** (CVSS) и ценность защищаемого ресурса;
4. **есть ли исправление** и сколько стоит его применить.

Способы устранения (от предпочтительных к вынужденным):

- **удалить** ненужный компонент (самая надёжная мера);
- **обновить** зависимость или базовый образ;
- **заменить** заброшенный компонент поддерживаемым аналогом;
- **уменьшить поверхность атаки**: slim-, distroless- или `scratch`-образы, multi-stage-сборка
(компиляторы и инструменты сборки не попадают в итоговый образ);
- **принять риск** с письменным обоснованием (правило ignore с `reason` или VEX-документ со статусом
`not_affected` и причиной) и сроком пересмотра.

### Часть 1. Инвентаризация: SBOM

> **Что сделать:**

### Часть 5. Security gate

> **Что сделать:** написать `scan.sh` и показать, что он не пропускает образы `:before` и пропускает `:after`.
> **В отчёт:** раздел 5 (листинг скрипта и политики, вывод и коды возврата). **Артефакт:** `scan.sh`.

Напишите скрипт `scan.sh <каталог> <образ>`. Он должен:

1. собрать образ;
2. построить SBOM (syft-json и CycloneDX) и сохранить его как артефакт сборки;
3. проверить SBOM командой grype с политикой `.grype.yaml`, игнорируя уязвимости без исправления
  и завершаясь с ненулевым кодом при находках уровня High и выше;
4. сохранить JSON-отчёт grype.

Продемонстрируйте, что скрипт **не пропускает** `before` и **пропускает** `after` (код возврата `echo $?`).

```bash
./scan.sh python-app lab4/v00-py:before; echo "exit=$?"    # ожидается 2
./scan.sh python-app lab4/v00-py:after;  echo "exit=$?"    # ожидается 0
```

Подумайте, почему gate проверяет **SBOM**, а не образ, и что делать с образами, которые уже работают
в продуктиве, когда выходит новая CVE.
