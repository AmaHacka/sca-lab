# Дополнительные задания (для любознательных)

Задания необязательные. Готовых инструкций здесь нет, только подсказки и ссылки:
разобраться предстоит самостоятельно. Результаты оформите в отчёте отдельным разделом
«Дополнительные задания».

## Д1. Достижимость уязвимого кода: govulncheck против grype

grype сообщает об уязвимости, если *версия модуля* попадает в уязвимый диапазон. `govulncheck` от команды Go
анализирует граф вызовов и сообщает только о тех уязвимостях, чьи *уязвимые функции реально вызываются*.

- Запустите `govulncheck` для Go-сервиса вашего варианта (исходного, до исправлений): в режиме исходного кода
  (`govulncheck ./...`) и в режиме бинаря (`govulncheck -mode=binary ./app`).
- Сравните с отчётом grype: сколько находок подтвердилось как достижимые? Объясните расхождения на 2–3 примерах.
- Как использовать эту информацию, не отказываясь от grype?

Подсказки: `go install golang.org/x/vuln/cmd/govulncheck@latest`; соберите и запускайте тем же тулчейном,
что указан в Dockerfile (например, в контейнере `golang:1.19-alpine`). Флаг `-show verbose` показывает
находки на уровне модулей и пакетов.
Ссылки: <https://go.dev/doc/security/vuln/>, <https://pkg.go.dev/golang.org/x/vuln/cmd/govulncheck>.

## Д2. VEX: машиночитаемое «нас это не касается»

Правило `ignore` в `.grype.yaml` действует только у вас. **VEX** (Vulnerability Exploitability eXchange)
позволяет поставщику ПО опубликовать заявление «продукт не подвержен уязвимости X, потому что…»,
которое учитывают сканеры потребителей.

- Для одной неприменимой уязвимости из вашего варианта (например, из задания Д1) создайте документ
  OpenVEX со статусом `not_affected` и подходящим `justification`.
- Покажите, что `grype <образ> --vex файл.json` перестаёт показывать эту находку, а с `--show-suppressed`
  показывает её как подавленную.
- Чем VEX лучше правила `ignore`? Кто и когда должен его выпускать?

Подсказки: утилита `vexctl` (`vexctl create --product=... --vuln=... --status=not_affected --justification=...`);
идентификатор продукта — purl образа или пакета. Ссылки: <https://openvex.dev>,
<https://github.com/openvex/vexctl>, раздел VEX в README grype.

## Д3. Сравнение сканеров

У каждого сканера свои источники данных и правила сопоставления, поэтому результаты различаются.

- Просканируйте один и тот же SBOM (CycloneDX) или образ вашего варианта инструментами grype,
  [Trivy](https://trivy.dev) и [OSV-Scanner](https://google.github.io/osv-scanner/).
- Сравните число находок по уровням и найдите 3–5 уязвимостей, которые находит только один из сканеров.
  Объясните причину для каждой: разные источники, разное сопоставление, ложное срабатывание, пропуск.

- Найдите в БД записи для CVE-2021-44228 и уязвимые диапазоны версий. Сравните с `grype db search`.
- Какие источники (providers) использует БД и как часто она обновляется? Как организовать работу grype

## Д5. Security gate в CI

- Перенесите ваш `scan.sh` в конвейер GitHub Actions или GitLab CI. Для GitHub есть готовые
  `anchore/sbom-action` и `anchore/scan-action`.
- SBOM должен сохраняться как артефакт сборки, а отчёт SARIF отображаться во вкладке Security
  (GitHub) или в отчёте о безопасности (GitLab).
- Как организовать регулярную (например, ночную) повторную проверку сохранённых SBOM уже выпущенных версий?

## Д6. Что изменилось между версиями

- Сравните SBOM «до» и «после» для одного из сервисов: какие компоненты добавились, удалились,
  сменили версию. Напишите для этого скрипт на jq или Python.
- Посчитайте, сколько уязвимостей устранено обновлением, а сколько — удалением компонентов.
